## The two conversions' own worked mechanism, for reference

Both conversions in this branch used the same two moves, and several CONVERT recommendations below
reuse them directly:

1. **Family-blocking -> `ruleFeatures` + `excludedMPRFeatures`** (the mpr-gated-exception pattern).
   The exceptional root gets `ruleFeatures="mprX"` directly; the rule that should refuse it gets
   `excludedMPRFeatures="mprX"` on its `MorphologicalInput`. This is producible ONLY when that rule
   is reached through an AffixTemplate `Slot` (HCLoader.cs:1717, `LoadAffixTemplate`'s own
   slot-blocking loop) -- the OPPOSITE placement requirement from a rule writing
   `MorphologicalOutput.MPRFeatures` (producible only OUTSIDE a Slot, `LoadInflAffixProcessRule`
   never sets it on an inflectional rule). Getting both halves of one bucket-2 pair genuinely
   producible sometimes means moving the reader into a template that didn't exist before
   (`languages/fusional-realizational-morphology`'s new `pastTemplate`) or moving a stray writer OUT
   of a template that already existed (`edge-cases/morphotactic-attribute-breadth`'s `mrConferExcl`).
2. **`morphologicalRuleOrder="linear"` -> `"unordered"`.** HCLoader hardcodes every `Stratum` to
   `Unordered` and can never emit `linear` (PROTOCOL.md section 9's fourth usage check). The fix is
   mechanical (flip the attribute) but the VERIFICATION is not: every word must be re-run against the
   C# founding oracle, because an unordered stratum can admit derivation orders a linear one refused,
   changing a word's analysis set. `morphotactic-attribute-breadth`'s own conversion found this
   changed NOTHING (verified, not assumed); `feature-gating-breadth`'s own pre-existing notes record
   that for ITS grammar the flip DOES add spurious parses, which is exactly why it stayed `false`
   rather than being flipped without re-deriving.
